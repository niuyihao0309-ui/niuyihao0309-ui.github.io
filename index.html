#01
多 Agent 平台

电商运营一站式 AI 助手

独有技术栈8 项
核心模块6 个
架构亮点3 条
体验入口 · 运营工作台在线体验 › 免登录直接体验云上实例：用演示数据跑通建店建档 → 商品池 → 投放实验 → 周期复盘。 GitHub 仓库源代码 → ShopPilot：FastAPI + Next.js 全栈源码，7 专家节点编排与幂等落库。
3~6 套一次生成主图方案
十几分钟出图（原数小时）
数十家商家在用

面向电商运营的一站式 AI 助手：把「商品诊断 → 创意生成 → 质量质检 → 人工审核 → 落库」编排成一条可恢复、可审计的 Agent 工作流，商家点一下即可拿到诊断结论与 3~6 套主图创意方案。

独有技术栈

Next.js 16 + React 19Celery + RedisPostgreSQL（Checkpoint）AI 图像 / 视频生成 SQLAlchemy / AlembicOpenTelemetryTailwind CSS 4ECharts

核心模块

Agent 平台7 个专家节点：上下文装配 → 诊断 → 创意策略 → 规则质检 → 条件返修 → 人工审核 → 幂等落库。
商品 / 店铺管理商品导入、SKU 库存管理与智能库存建议。
素材生成创意计划制定，AI 图片 / 视频生成任务异步执行。
广告运营广告实验、投放推荐与效果数据导入分析。
竞品监控竞品链接解析与定时监控追踪。
工作区多用户认证体系与工作台数据聚合。

架构亮点

◆旗舰流程拆为 7 个专家节点（上下文装配 → 诊断 → 创意策略 → 规则质检 → 条件返修 → 人工审核 → 幂等落库），并注册竞品监控、投放实验等共 7 条工作流按关键词自动路由。
◆人工审核基于 interrupt + Checkpoint 实现「暂停 — 恢复」：状态落 PostgreSQL 释放 worker，前端「通过 / 改后通过 / 驳回」后由 Command(resume) 断点续跑；「interrupt 之前不产生副作用」，落库收敛到幂等 finalize 节点。
◆Outbox 模式保证「写业务数据」与「派发任务」原子一致；worker 侧租约 + 心跳续期 + fencing token 吸收重复执行；工具风险分级 R0~R3，统一走 ToolGateway 四层校验。

AI 客服

电商场景任务型 AI 客服

独有技术栈5 项
核心模块6 个
架构亮点3 条
体验入口 · 客服窗口在线体验 › 一句话完成查订单、查物流、退款咨询 —— 体验懂业务、守边界的 AI 客服，右侧带 3D 数字人应答。 GitHub 仓库源代码 → ChatPilot：对话引擎源码，意图理解 + YAML 流程编排 + 接口调用。
数百次日均会话量
七成会话自助闭环
↓70%人工转接量

电商场景的 AI 客服：用户一句话完成查订单、查物流、问商品、退款咨询与转人工。核心思路是大模型只做意图理解与结构化规划，业务动作交给流程、规则和接口，兼顾自然语言理解能力与业务可控性。

独有技术栈

MySQL（aiomysql）YAML 流程配置Jinja2 提示词模板 uv 包管理电商 Mock 后端

核心模块

plan 意图规划TurnPlanner 用 LLM 做意图理解与结构化规划，TurnPlanValidator 防幻觉校验。
task 任务轨道命令 / 流程 / 动作驱动的业务办理引擎，执行查单、退款等实际操作。
knowledge 知识轨道商品、订单、售后政策咨询问答。
chitchat + clarify闲聊兜底与澄清话术生成，保证对话不中断。
engine / service 编排层DialogueEngine 单轮编排，DialogueService 负责状态加载与保存。
flow_config 流程配置6 条业务流 + 6 条系统过场流、8 个槽位、47 个步骤节点声明式编排，业务改动无需改代码。

架构亮点

◆三轨分流：每轮消息先由 TurnPlanner 调大模型输出结构化 TurnPlan，按 task / knowledge / chitchat 唯一轨道分发，从源头避免「一句话干多件事」的失控。
◆五重防幻觉校验：轨道唯一性、命令白名单、单流程启动、流程存在性、知识意图与聚焦对象；任一失败即转澄清话术或引导转人工，绝不带着错误状态继续执行。
◆YAML 声明式流程编排：6 条业务流 + 6 条系统过场流、8 个槽位、47 个步骤节点；聚合根 JSON 落库多轮状态，挂起栈支持「查物流途中问客服电话」式打断与恢复。

面向连锁零售品牌的合同审批智能审查：把采购 / 销售 / 门店租赁合同从 Word、PDF、扫描件解析为可溯源的结构化条款，用「规则引擎 + 大模型」双引擎识别法律与商业风险，输出修改示范条款并幂等回写审批意见。

独有技术栈

MySQL 8（asyncmy）python-docx / PyMuPDFRapidOCR（扫描件） Element PlusPiniaVite 5

核心模块

文档接入解析DOCX / PDF / 扫描件 OCR 统一归一为可溯源的 blocks 中间表示。
智能合规审查13 条规则引擎先行 + LLM 语义研判，输出风险等级与法律依据。
交互研判建议原文与风险卡片双向高亮跳转、条款差异对比、示范条款生成。
审批集成回写审查意见幂等回写审批系统评论区，支持导出 Markdown / PDF 报告。

架构亮点

◆DOCX / PDF / 扫描件三路解析管线归一为 blocks 中间表示（block_id + 字符区间），风险项与批注只引用地址不存裸文本，保证前端高亮与原文永远对得上。
◆规则先行、大模型只补语义：13 条规则管确定性判定，大模型只研判高危表述并强制 Pydantic 结构化输出，标准合同不误报。
◆工作台原文与风险卡片双向高亮跳转、条款级差异对比、示范条款一键复制；意见经幂等键回写审批评论区；三角色 21 权限点，前后端共用同一份权限矩阵并由测试钉住一致性。

面向企业文档的私有化知识库问答系统：PDF / 图文资料批量入库，自然语言提问即可拿到带出处的答案，替代「翻文档 + 问老员工」的低效检索方式。

独有技术栈

Milvus 向量库MongoDB（会话历史）MinIO（原件存储） Rerank 重排MCP 联网搜索

核心模块

文档导入流水线PDF 转 Markdown → 图片识别 → 条目名识别 → 分块 → BGE 向量化 → 入 Milvus，6 节点 LangGraph 图。
智能问答流水线条目确认 → 向量检索 / HyDE → MCP 联网搜索 → RRF 混合召回 → Rerank → 流式答案生成。
Web API 层导入服务（8001）与查询服务（8003）分离，SSE 实时推送处理进度。
前端页面import.html 导入页、chat.html 对话页、index.html 导航页，原生 HTML 轻量实现。
基础设施编排start_all.bat 一键拉起 Docker 全套中间件，健康检查通过后启动双后端。

架构亮点

◆双 LangGraph 状态图（文档导入 / 知识问答）：导入侧完成 PDF→Markdown 解析、图片抽取、切片与向量化入库；问答侧完成主体确认、多路召回、融合重排与生成，节点可插拔、可单独调试。
◆三路并行召回：BGE-M3 稠密 + 稀疏混合向量、HyDE 假设文档召回、MCP 联网搜索补充实时信息；RRF（k=60）加权融合 + Reranker 精排，明显改善长尾问题召回质量。
◆主体名确认前置节点：指向多个相似规格时反问收敛（如「P60 128G / P60 Art」），库中查无此主体直接拒答，避免模型脱离知识库臆造；存储按职责拆分 —— Milvus 存向量、MinIO 存原件、MongoDB 存会话历史。

#05
NL2SQL 取数

企业经营数据智能取数平台

独有技术栈5 项
核心模块6 个
架构亮点4 条
GitHub 仓库源代码 → DataPilot：NL2SQL 源码，Schema 三路召回 + SQL 自修复闭环。
分钟级出数（原数个工作日）
100+每月省下工时
80%+一次问数正确率

面向企业内部的经营数据查询（NL2SQL）平台：把运营、商品、门店等角色的取数需求收进同一个入口 —— 用中文直接问经营指标、按地区 / 门店与时间维度看数、做多期趋势与占比对比，都能拿到结果表与图表，不用懂 SQL，也不必再走「提需求 → 等数据组排期出数」的老路。

独有技术栈

NL2SQL 引擎Qdrant 向量库Elasticsearch（字段取值） jieba 分词图表自动推断

核心模块

Schema 三路召回jieba 分词提关键词后并行召回：字段与指标走 BGE + Qdrant 向量检索，字段取值走 Elasticsearch 全文检索。
Schema 归并三路结果合并去重，指标补齐关联列、取值回填为字段样例、按表分组并补主外键，汇成最小可用 Schema。
SQL 生成大模型过滤无关表列后，只按相关 Schema 生成单条只读查询语句。
校验与自修复EXPLAIN 预检 → 执行 → 报错携 Schema 上下文回灌重写，形成自愈闭环。
结果即报表按列特征自动推断图表类型：折线看趋势、饼图看占比、柱状比大小。
流式取数反馈SSE 逐步推送取数进度，过程对使用方透明可见。

架构亮点

◆用 LangGraph 把一次取数编排成 12 个节点的链路：jieba 分词提关键词后三路并行召回 —— 字段与指标走 BGE + Qdrant 向量检索，字段取值（如「华北」「华东」）走 Elasticsearch 全文检索；再把三路结果合并去重（指标补齐关联列、取值回填为字段样例、按表分组并补主外键），汇成一份最小可用 Schema 交给大模型生成 SQL。
◆召回后再用大模型过滤表与列，只把与问题相关的表和字段喂给生成节点，压住无关 Schema 的干扰；同时把当前时间（日期 / 星期 / 季度）与数据库方言一并注入提示词，让「上个月」「本季度」这类相对时间与函数写法有据可依。
◆生成 — 校验 — 自修复闭环：生成的单条只读 SQL 先用 EXPLAIN 预检，通过则执行；报错则把异常信息连同 Schema 上下文回灌大模型重写后再执行，避免因字段名或语法小错直接失败；提示词层约束只出查询语句、禁止写操作与多语句拼接。
◆结果即报表：执行结果按列特征自动推断图表类型 —— 时间维度出折线看趋势、问占比出饼图、其余出柱状比大小；配合 SSE 逐步推送「提取关键字 → 召回 → 过滤 → 生成 SQL → 校验 → 执行」的进度，取数过程对使用方透明可见。
